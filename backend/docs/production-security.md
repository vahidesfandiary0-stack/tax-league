# چک‌لیست امنیت انتشار

## تنظیمات production

سرور را با تنظیمات production اجرا کنید:

```bash
DJANGO_SETTINGS_MODULE=config.settings.production
```

این تنظیمات عمداً در صورت نبودن کلید قوی، PostgreSQL، دامنه‌های مجاز یا خاموش نبودن DEBUG متوقف می‌شود. متغیرهای لازم را از فایل نمونه ریشه پروژه بردارید و مقادیر واقعی را فقط در secret manager یا محیط امن میزبان قرار دهید.

قبل از انتشار:

1. گواهی TLS معتبر روی reverse proxy نصب و تمدید خودکار آن فعال باشد.
2. مقدارهای `DJANGO_ALLOWED_HOSTS`، `DJANGO_CSRF_TRUSTED_ORIGINS` و `DJANGO_CORS_ALLOWED_ORIGINS` دقیق و محدود باشند.
3. `DJANGO_SECURE_SSL_REDIRECT=true` فقط وقتی فعال باشد که proxy هدر `X-Forwarded-Proto: https` را درست تنظیم می‌کند.
4. HSTS را فقط پس از اطمینان از HTTPS کامل دامنه فعال نگه دارید؛ includeSubDomains و preload نیازمند بررسی همه زیردامنه‌ها هستند.
5. `python manage.py check --deploy --settings=config.settings.production` اجرا و همه هشدارها بررسی شوند.
6. `python manage.py migrate --settings=config.settings.production` و سپس `python manage.py collectstatic --noinput --settings=config.settings.production` اجرا شوند.
7. `python manage.py sync_staff_roles --settings=config.settings.production` اجرا و عضویت کارکنان توسط superuser بازبینی شود.
8. `MEDIA_ROOT` روی volume خصوصی باشد؛ وب‌سرور نباید مسیر media یا پوشه رسیدها را عمومی سرو کند.
9. endpoint دانلود رسید فقط از طریق API احراز هویت‌شده و مجاز قابل دسترسی باشد.
10. فایل‌های پشتیبان رمزگذاری‌شده، خارج از سرور اصلی نگهداری و بازیابی آن‌ها به‌صورت دوره‌ای تمرین شود.

## مدیریت اسرار و داده‌های حساس

- فایل `.env`، کلید Django، رمز دیتابیس، کلیدهای پیامک و اطلاعات واقعی پرداخت را در Git قرار ندهید.
- کلید `DJANGO_SECRET_KEY` باید تصادفی، منحصربه‌فرد و حداقل ۵۰ نویسه باشد؛ در صورت افشا آن را تعویض کنید.
- BasicAuthentication در production حذف شده است. توکن‌های API باید محرمانه بمانند و TLS اجباری باشد.
- شماره کارت و نام صاحب حساب در مدل فعلی به‌صورت متن ذخیره می‌شوند؛ تا زمان پیاده‌سازی رمزنگاری در سطح برنامه یا secret store، دسترسی دیتابیس و پشتیبان‌ها باید به‌شدت محدود شود. این داده نباید در log، export یا گزارش عمومی ظاهر شود.
- فایل رسید از نظر پسوند، اندازه و امضای ابتدایی بررسی می‌شود، اما این بررسی جایگزین malware scanning و اعتبارسنجی کامل PDF/تصویر نیست. قبل از استفاده عمومی، اسکن بدافزار و ذخیره‌سازی خصوصی امن اضافه شود.
- ثبت رویداد مدیریتی فعلی در Django Admin Log است؛ برای رویدادهای حساس، نگهداری append-only خارج از دیتابیس اصلی و هشدار تغییر/حذف نیز در مرحله سخت‌سازی بعدی لازم است.

## پشتیبان‌گیری PostgreSQL

سیاست نمونه: پشتیبان روزانه رمزگذاری‌شده، نگهداری چندنسخه‌ای، کپی خارج از میزبان و آزمون بازیابی ماهانه. فایل dump خام شامل داده شخصی است و نباید در Git یا فضای عمومی قرار گیرد.

نمونه dump:

```bash
pg_dump --format=custom --no-owner "$DATABASE_URL" --file "tax-league-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

این دستور به‌تنهایی رمزگذاری یا انتقال امن انجام نمی‌دهد؛ فایل خروجی باید بلافاصله با ابزار سازمانی رمزگذاری و به مقصد خصوصی منتقل شود. دسترسی، دوره نگهداری و حذف امن باید مستند باشد.

## وضعیت

این تغییرات تنظیمات کدنویسی را سخت‌گیرانه‌تر می‌کند؛ هیچ سرور، TLS، backup، رمزنگاری فیلد کارت یا malware scanner در این commit راه‌اندازی نشده است. پیش از ادعای آمادگی انتشار باید چک‌لیست بالا اجرا و بازبینی شود.


## آزمون‌های زمان‌بندی‌شده سراسری

برای آزمونی که `starts_at` دارد، تمام شرکت‌کنندگان یک `started_at` و `deadline_at` مشترک می‌گیرند. ورود دیرهنگام زمان اضافه ایجاد نمی‌کند؛ ثبت پاسخ در زمان پایان یا پس از آن رد می‌شود و تحویل زودهنگام آزمون زمان‌بندی‌شده نیز مجاز نیست.

برای نهایی‌سازی نتیجه افرادی که برنامه را بسته‌اند یا اتصالشان قطع شده، دستور زیر را با cron هر دقیقه اجرا کنید:

```cron
* * * * * cd /opt/tax-league/backend && DJANGO_SETTINGS_MODULE=config.settings.production /opt/tax-league/venv/bin/python manage.py finalize_expired_attempts
```

مسیرها را مطابق محل نصب واقعی تغییر دهید. این دستور حداکثر ۵۰۰ تلاش منقضی‌شده را در هر اجرا پردازش می‌کند؛ در صورت عقب‌ماندگی، اجراهای بعدی صف را تخلیه می‌کنند. قبل از مسابقه واقعی، اجرای cron، زمان‌بندی سرور، بار دیتابیس و پردازش هم‌زمان ۵۰۰۰ شرکت‌کننده باید در محیط آزمایشی بررسی شوند.
