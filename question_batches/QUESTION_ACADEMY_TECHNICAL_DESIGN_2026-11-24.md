# طرح فنی مرحله‌ای ارتقای بانک سؤال و آکادمی RAQTIVA
تاریخ: ۱۴۰۵/۰۹/۰۳ (2026-11-24)
شاخه: `question-bank/research-20261124`

> این سند طرح اجرایی است، نه اجرای تغییرات. تا پیش از بررسی migrationها، تست‌ها و سازگاری موبایل، هیچ تغییری در شاخه اصلی، پایگاه داده عملیاتی یا سرور اعمال نمی‌شود.

## ۱. اصول غیرقابل‌تغییر
- آزمون شبانه رایگان و نامحدود می‌ماند.
- فقط نتیجه معتبر آزمون شبانه در رتبه‌بندی ملی و استانی اثر دارد.
- اشتراک و آکادمی، XP، تمرین و محتوای آموزشی نباید امتیاز یا رتبه رقابتی ایجاد یا تغییر دهند.
- سؤال منتشرشده بدون تأیید منبع، پاسخ یکتا، کنترل تکراری، بازبینی مستقل و تأیید مالک منتشر نمی‌شود.
- محتوای دام‌شناسی و تاکتیک حل فقط در API آکادمی و برای اشتراک فعال قابل دسترسی است.

## ۲. تغییرات پیشنهادی مدل داده

### ۲.۱ دشواری
گزینه‌های مستقل به مدل دشواری اضافه شوند:
- `hard` = سخت
- `very_hard` = خیلی سخت
- `specialized` = تخصصی

مقادیر قدیمی `easy` و `medium` در migration حفظ شوند تا داده قبلی از بین نرود؛ ولی سیاست انتشار بانک جدید، پذیرش آن‌ها را مسدود کند. تبدیل خودکار داده‌های قبلی به دشواری جدید ممنوع است. برای هر سؤال قدیمی تعیین سطح باید جداگانه انجام شود.

### ۲.۲ منبع حقوقی نسخه‌پذیر
به‌جای اتکا به یک رشته متنی `source_reference`، موجودیت منبع حقوقی ساخت‌یافته پیشنهاد می‌شود با حداقل:
- نوع سند (قانون، آیین‌نامه، بخشنامه، رأی/دستورالعمل رسمی)
- عنوان رسمی سند
- ماده، تبصره، بند و جزء
- مرجع تصویب/ابلاغ
- تاریخ تصویب و انتشار، در صورت وجود
- نشانی منبع رسمی
- تاریخ شروع و پایان اعتبار
- یادداشت اصلاحات و نسخه مورد استناد

سؤال می‌تواند به یک یا چند منبع متصل شود. مقدار متنی فعلی برای سازگاری قدیمی حفظ و در مرحله انتقال داده مهاجرت تدریجی شود.

### ۲.۳ پاسخ‌نامه عمومی
پاسخ‌نامه عمومی ساختار مستقل و زمان انتشار داشته باشد:
- توضیح استدلالی پاسخ صحیح
- تحلیل جداگانه هر چهار گزینه
- ارجاع دقیق به منبع حقوقی
- زمان مجاز شدن نمایش پاسخ‌نامه
- نسخه پاسخ‌نامه و سابقه تغییرات

**محدودیت امنیتی:** endpoint دریافت سؤال در زمان آزمون نباید `is_correct`، توضیح، پاسخ‌نامه یا محتوای آکادمی را برگرداند. پاسخ‌نامه فقط پس از ثبت نهایی آزمون/پاسخ و مطابق سیاست محصول ارائه شود.

### ۲.۴ محتوای آکادمی
مدل جداگانه و رابطه یک‌به‌یک یا یک‌به‌چند با سؤال:
- دام یا نکته انحرافی
- علت جذابیت هر گزینه غلط
- خطاهای رایج داوطلب
- روش تحلیل و حل
- راهبرد مدیریت زمان
- هشدارهای دقت و حدود اعتبار تحلیل
- نسخه و وضعیت بازبینی محتوا

این داده‌ها نباید در serializer عمومی سؤال یا پاسخ‌نامه عمومی قرار گیرند.

## ۳. مجوزدهی اشتراک
- مجوز آکادمی باید در سمت سرور بررسی شود؛ پنهان‌کردن دکمه در Flutter کافی نیست.
- وضعیت اشتراک از منبع معتبر پرداخت/اشتراک سمت سرور خوانده شود.
- اشتراک منقضی، لغوشده، نامعتبر یا تأییدنشده دسترسی ندهد.
- endpoint آکادمی در حالت پیش‌فرض deny باشد.
- پاسخ‌های API آکادمی در cache عمومی یا cache مشترک کاربران ذخیره نشوند.
- رویدادهای دسترسی و رد دسترسی برای عیب‌یابی و ممیزی ثبت شوند.
- خرید اشتراک هیچ مسیر تغییری به امتیاز، رتبه، زمان آزمون یا انتخاب سؤال نداشته باشد.

## ۴. چرخه تأیید و انتشار
چرخه پیشنهادی:
`draft → pending_review → approved → published`

شرایط ورود به بازبینی:
- دقیقاً چهار گزینه
- دقیقاً یک پاسخ صحیح
- منبع رسمی قابل بررسی و تاریخ اعتبار
- توضیح پاسخ عمومی کامل
- عدم تکرار یا شباهت ناموجه با بانک
- تعیین دشواری و موضوع

شرایط تأیید:
- بازبین با نویسنده متفاوت باشد.
- بازبین منبع و پاسخ یکتا را مستقلاً بررسی کند.
- تغییر پس از تأیید، تأیید قبلی را باطل و نسخه جدید ایجاد کند.
- انتشار نیازمند تأیید نهایی مالک باشد؛ تأیید فنی بازبین به‌تنهایی مجوز انتشار نیست.

## ۵. قرارداد API پیشنهادی
نام مسیرها نمونه طراحی‌اند و پیش از کدنویسی باید با الگوی URL فعلی پروژه تطبیق داده شوند.

- فهرست/جزئیات سؤال منتشرشده: فقط متن و گزینه‌های بدون کلید پاسخ.
- پاسخ‌نامه عمومی: فقط بعد از تحقق شرط مجاز نمایش؛ شامل توضیح و تحلیل گزینه‌ها و منبع.
- محتوای آکادمی: endpoint مستقل با کنترل اشتراک فعال و پاسخ مستقل.
- وضعیت اشتراک: استفاده از endpoint فعلی اشتراک؛ از ساخت منبع حقیقت دوم اجتناب شود.

هیچ endpoint عمومی نباید با پارامتر دلخواه کاربر، پاسخ صحیح یا محتوای آکادمی را زودتر افشا کند.

## ۶. آزمون‌های پذیرش ضروری
1. چهار گزینه و دقیقاً یک پاسخ صحیح؛ صفر یا دو پاسخ صحیح رد شود.
2. نویسنده نتواند سؤال خود را بازبینی یا تأیید کند.
3. سؤال فاقد منبع/اعتبار حقوقی یا دارای منبع منقضی قابل انتشار نباشد.
4. پاسخ صحیح، توضیح و محتوای آکادمی در API آزمون قابل مشاهده نباشند.
5. پاسخ‌نامه عمومی قبل از زمان مجاز قابل دریافت نباشد.
6. کاربر فاقد اشتراک فعال با درخواست مستقیم HTTP نیز پاسخ 403 بگیرد.
7. اشتراک منقضی/لغوشده/تأییدنشده دسترسی آکادمی ندهد.
8. محتوای آکادمی کاربر A به کاربر B نشت نکند.
9. پرداخت/اشتراک هیچ تغییری در score، rank، XP یا eligibility آزمون ایجاد نکند.
10. مهاجرت داده‌های فعلی بدون حذف یا تغییر ناخواسته رکوردها اجرا شود.
11. API موبایل قدیمی تا زمان انتشار نسخه سازگار دچار شکست نشود.
12. سؤال منتشرشده immutable بماند؛ اصلاح با نسخه جدید و ممیزی انجام شود.

## ۷. ترتیب اجرای کم‌ریسک
مرحله A — ممیزی تکمیلی:
- بررسی همه migrationها، سرویس‌های انتشار، permissionها، اشتراک و تست‌های موجود.
- تعیین محل دقیق کنترل نتیجه نهایی آزمون و زمان نمایش پاسخ‌نامه.
- ثبت قرارداد API موبایل فعلی.

مرحله B — طرح migration:
- افزودن دشواری‌ها و مدل‌های منبع/پاسخ‌نامه/آکادمی با سازگاری عقب‌رو.
- تولید migration و بررسی SQL/plan؛ بدون اجرای عملیاتی.

مرحله C — پیاده‌سازی امن:
- serializerها و endpointهای جداگانه.
- permission سمت سرور برای اشتراک.
- ثبت ممیزی و عدم cache محتوای پولی.

مرحله D — آزمون:
- تست واحد، API، permission، migration، امنیت افشای پاسخ و regression موبایل.
- آزمون سناریوهای اشتراک و بازیابی خرید.

مرحله E — انتشار کنترل‌شده:
- فقط پس از موفقیت تست‌ها، backup معتبر، تأیید مالک و برنامه بازگشت.
- ابتدا محیط آزمایشی؛ سپس انتشار عملیاتی با تأیید صریح.

## ۸. مواردی که هنوز تصمیم/شاهد لازم دارند
- سیاست دقیق زمان نمایش پاسخ‌نامه عمومی: پس از پاسخ هر سؤال، پس از پایان آزمون، یا پس از پایان پنجره آزمون شبانه.
- قرارداد فعلی اشتراک و نام permission/service واقعی در کد؛ باید در ممیزی تکمیلی استخراج شود.
- سیاست نسخه‌بندی منابع حقوقی و محتوای آکادمی.
- نقش و سازوکار تأیید نهایی مالک در پنل مدیریت.
