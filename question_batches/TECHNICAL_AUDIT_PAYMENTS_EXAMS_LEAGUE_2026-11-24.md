# گزارش ممیزی فنی پرداخت، اشتراک، آزمون و لیگ
تاریخ: ۱۴۰۵/۰۹/۰۳
مبنای بررسی: شاخه `main` مخزن `vahidesfandiary0-stack/tax-league`
وضعیت: ممیزی ایستا بر اساس کد منبع؛ بدون اجرای تست، بدون تغییر کد و بدون دسترسی به محیط عملیاتی.

## خلاصه مدیریتی
در مخزن، مسیر پایه سفارش و پرداخت کارت‌به‌کارت وجود دارد: مشاهده طرح‌ها، ساخت سفارش، ارسال رسید، بررسی مدیر و اعطای اشتراک یا دسترسی آزمون. اما این مسیر، در وضعیت فعلی کد، درگاه خودکار کافه‌بازار/Poolakey را اثبات نمی‌کند. همچنین مدل اشتراک و کنترل دسترسی برای آزمون پولی وجود دارد، ولی زیرساخت مستقل و قابل‌ممیزی برای محتوای اختصاصی آکادمی و مجوز دسترسی آن در API مشاهده نشد.

چرخه آزمون شامل شروع، ذخیره پاسخ، تحویل، نتیجه و ثبت امتیاز لیگ است. با این حال، نوع آزمون شبانه به‌صورت نوع مستقل مدل نشده و عضویت در لیگ با پرچم عمومی `counts_for_league` کنترل می‌شود؛ این طراحی به‌تنهایی تضمین نمی‌کند فقط آزمون شبانه رسمی وارد رتبه‌بندی شود.

## ۱. پرداخت و اشتراک

### موارد موجود
- `PaymentOrder` با وضعیت‌های `awaiting_payment`, `under_review`, `approved`, `rejected`, `cancelled` و مبلغ ثابت‌شونده پس از ایجاد وجود دارد.
- رسید با پسوندهای JPG/JPEG/PNG/PDF، سقف ۵ مگابایت و بررسی امضای ابتدایی فایل اعتبارسنجی می‌شود.
- کاربر فقط سفارش‌های خودش را فهرست/مشاهده و برای سفارش خودش رسید ارسال می‌کند.
- تأیید و رد سفارش از طریق action پنل مدیریت انجام می‌شود؛ سرویس تأیید، اشتراک یا دسترسی آزمون را در تراکنش ایجاد می‌کند.
- تمدید اشتراک فعال، از انتهای آخرین اشتراک فعالِ منقضی‌نشده ادامه می‌یابد.
- API وضعیت اشتراک جاری را با `starts_at <= now < ends_at` و وضعیت فعال برمی‌گرداند.
- رسید دانلودی از مسیر staff فقط برای superuser یا کارمند دارای مجوز `payments.view_paymentorder` قابل دسترسی است.

### شکاف‌ها و ریسک‌ها
1. **اتصال خودکار کافه‌بازار در کد بررسی‌شده پیدا نشد.** در اپ پرداخت، مدل‌ها و سرویس‌های موجود، مسیر قابل مشاهده بر پایه بارگذاری رسید و تأیید دستی مدیر است. endpointهای سفارش/رسید وجود دارند؛ endpointهای ثبت توکن خرید، verify، restore یا callback بازار در این اپ دیده نشدند. بنابراین آماده‌بودن واقعی Poolakey از این ممیزی قابل تأیید نیست.
2. **اشتراک فقط در نقطه شروع آزمون پولی کنترل می‌شود.** سرویس `start_attempt` برای آزمون دارای `requires_purchase`، دسترسی خرید آزمون یا اشتراک فعال را بررسی می‌کند؛ این کنترل برای محتوای آکادمی قابل استفاده نیست مگر endpointهای آکادمی نیز آن را صریحاً اعمال کنند.
3. **هیچ مدل/endpoint مستقل آکادمی در فهرست اپ‌های backend مشاهده نشد.** در نتیجه کنترل دسترسی اشتراکی برای محتوای آموزشی، تله‌ها و تحلیل اختصاصی هنوز از کد موجود قابل اثبات نیست.
4. **چرخه انقضا/ابطال اشتراک در سطح مدل ساده است.** وضعیت‌های active/expired/revoked تعریف شده‌اند، اما سرویس زمان‌بندی‌شده یا مسیر عملیاتی تغییر خودکار active به expired در فایل‌های بررسی‌شده دیده نشد. API با زمان جاری دسترسی مؤثر را می‌سنجد، پس انقضای دسترسی حتی با باقی‌ماندن status=active رد می‌شود؛ با این حال پاک‌سازی وضعیت و گزارش مدیریتی نیازمند بررسی تکمیلی است.
5. **تنظیمات پرداخت بانکی فقط برای superuser قابل مدیریت است.** این محدودیت ممکن است عملیاتی و عمدی باشد، اما باید با نقش‌های مالی مورد انتظار تطبیق داده شود.

## ۲. آزمون و محرمانگی پاسخ
- آزمون منتشرشده، تلاش کاربر را با snapshot مستقل از متن سؤال/گزینه‌ها ایجاد می‌کند.
- گزینه صحیح در serializer آزمون ارسال نمی‌شود؛ پاسخ صحیح در محاسبه سمت سرور استفاده می‌شود.
- پاسخ فقط برای سؤال همان تلاش و گزینه متعلق به همان snapshot پذیرفته می‌شود.
- برای هر کاربر/آزمون یک تلاش فعال با قید یکتای دیتابیس محدود شده است.
- زمان از ساعت سرور محاسبه می‌شود؛ پاسخ بعد از deadline رد می‌شود.
- نتیجه فقط برای مالک تلاش از API نتیجه قابل مشاهده است.
- نهایی‌سازی idempotent طراحی شده و امتیاز از snapshot سمت سرور محاسبه می‌شود.

### شکاف‌ها و ریسک‌ها
1. `Exam.Kind` فقط daily/weekly/mock دارد و نوع مستقل `night` وجود ندارد.
2. `counts_for_league` یک Boolean عمومی است؛ سرویس ثبت امتیاز صرفاً همین پرچم را کنترل می‌کند. بنابراین قاعده محصول «فقط آزمون شبانه رسمی امتیاز لیگ بگیرد» در سطح مدل/سرویس به‌صورت سخت‌گیرانه enforce نشده است.
3. API فعلی لیگ یک فهرست عمومی فصل ارائه می‌کند. در endpoint و aggregation بررسی‌شده، فیلتر رتبه‌بندی استانی و شرط `province_verified` مشاهده نشد؛ تحقق لیگ استانی از کد فعلی قابل تأیید نیست.
4. فیلد `explanation` در snapshot سؤال ذخیره می‌شود، اما serializer نتیجه فقط امتیاز، تعداد صحیح/غلط/بی‌پاسخ و زمان تحویل را برمی‌گرداند. پاسخ‌نامه تشریحی عمومی پس از تحویل در این API ارائه نمی‌شود.
5. هیچ endpoint نتیجه‌ای که توضیح عمومی هر گزینه، استناد قانونی و نسخه منبع را برگرداند در مسیرهای بررسی‌شده وجود ندارد. این مورد باید با استاندارد بانک سؤال و زمان‌بندی افشای پاسخ‌نامه طراحی شود.
6. قاعده tie-break در leaderboard موجود است: امتیاز، صحیح بیشتر، غلط کمتر، زمان کمتر و شناسه کاربر. این با ترتیب مورد انتظار محصول هم‌راستاست.

## ۳. قراردادهای API کشف‌شده

### پرداخت
- `GET /api/v1/payments/plans/`
- `GET /api/v1/payments/subscription/me/`
- `GET /api/v1/payments/instructions/`
- `GET /api/v1/payments/orders/`
- `POST /api/v1/payments/orders/create/`
- `GET /api/v1/payments/orders/{order_id}/`
- `POST /api/v1/payments/orders/{order_id}/submit/`
- `GET /api/v1/payments/staff/orders/{order_id}/receipt/`

تأیید/رد سفارش در actionهای Django Admin انجام می‌شود، نه در endpoint عمومی موبایل.

### آزمون
- `GET /api/v1/exams/`
- `GET /api/v1/exams/focus-status/`
- `GET /api/v1/exams/results/`
- `POST /api/v1/exams/{exam_id}/start/`
- `POST /api/v1/exams/attempts/{attempt_id}/answers/`
- `POST /api/v1/exams/attempts/{attempt_id}/finalize/`
- `GET /api/v1/exams/attempts/{attempt_id}/result/`

### لیگ
- `GET /api/v1/league/...` شامل فصل فعال، جدول رتبه‌بندی، آمار من و اعتراض؛ مسیرهای دقیق در `backend/apps/league/urls.py`.

## ۴. موبایل
- `mobile/lib/main.dart` شامل پیاده‌سازی بخش عمده اپ است.
- در کد آزمون، مسیرهای API شروع، پاسخ، تحویل و نتیجه با قراردادهای backend هم‌نام هستند.
- در زمان قطع اینترنت، پاسخ‌های انتخابی در ذخیره‌سازی امن محلی نگه‌داری و سپس ارسال می‌شوند؛ تحویل تا همگام‌سازی کامل پاسخ‌ها غیرفعال است.
- در بخش پرداخت، از این ممیزی نمی‌توان جریان واقعی Poolakey/تأیید خرید بازار را تأیید کرد. بررسی کامل همه مسیرهای UI و فایل‌های build موبایل در مرحله بعد لازم است.

## ۵. تست‌ها و مهاجرت‌ها
- در مخزن تست‌های مرتبط موجودند: `test_exams.py`, `test_exam_attempt_api.py`, `test_exam_results_api.py`, `test_synchronized_exam.py`, `test_league.py` و `test_exam_focus_mode.py`.
- مهاجرت‌های آزمون شامل `0001_initial`, `0002_exam_purchase_fields`, `0004_attempt_integrity_constraints` هستند؛ در فهرست migrations نسخه `0003` دیده نشد، که ممکن است شماره‌گذاری حذف‌شده/تاریخچه شاخه باشد و باید در بررسی dependency graph روشن شود.
- مهاجرت‌های پرداخت شامل `0001_initial`, `0002_paymentorder_plan`, `0003_purchasedexamaccess` هستند.
- تست‌ها در این مرحله فقط از روی فهرست فایل‌ها شناسایی شده‌اند؛ **هیچ تستی اجرا نشده است** و نتیجه پاس/فیلد اعلام نمی‌شود.
- تطبیق migration graph کامل، وضعیت migrations محیط عملیاتی و اختلاف کد main با سرور بدون دسترسی به محیط اجرا قابل تأیید نیست.

## ۶. اولویت اصلاح پیشنهادی (بدون اجرای تغییر در این مرحله)
1. **درآمد/اشتراک:** تعیین مسیر قطعی فروش نسخه اول: کارت‌به‌کارت دستی یا کافه‌بازار. اگر بازار مسیر اصلی است، ممیزی و تکمیل مستقل Poolakey + verify/restore سمت سرور + idempotency + ثبت رویداد خرید لازم است.
2. **آکادمی:** تعریف entitlement مرکزی سمت سرور با سیاست deny-by-default، و اعمال آن در تمام endpointهای محتوا/فایل/پاسخ/AI؛ سپس آزمون مستقیم HTTP برای کاربر فاقد اشتراک، منقضی و لغوشده.
3. **عدالت آزمون:** افزودن نوع آزمون رسمی شبانه یا قاعده محدودکننده معادل؛ حذف امکان امتیازدهی لیگ برای سایر انواع آزمون مگر با مجوز صریح مالک.
4. **لیگ استانی:** طراحی scope استانی و فیلتر قطعی `province_verified`، بدون تغییر در رتبه ملی و قواعد امتیاز.
5. **پاسخ‌نامه:** endpoint جداگانه پس از تحویل با تحلیل عمومی امن و منبع حقوقی نسخه‌دار؛ محتوای تله‌شناسی/راهبردی فقط از مسیر entitlement آکادمی.
6. **تست:** اجرای suite در محیط ایزوله، افزودن تست‌های منفی مجوز و آزمون‌های مرزی، سپس مقایسه قرارداد API با Flutter.
7. **مهاجرت و انتشار:** طراحی migration سازگار با داده قبلی؛ backup و تأیید مالک قبل از هر تغییر عملیاتی.

## ۷. مرز این اقدام
این سند صرفاً یافته‌های ممیزی ایستای کد شاخه `main` را ثبت می‌کند. هیچ فایل اجرایی، migration، داده، API، سرور، APK یا تنظیم عملیاتی تغییر نکرده است. برای تبدیل این یافته‌ها به اصلاحات، ابتدا باید تست‌های موجود و قراردادهای موبایل به‌طور کامل بررسی و در محیط ایزوله اجرا شوند.
